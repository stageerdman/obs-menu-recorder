## Recently fixed, needs confirmation on real hardware/connection
- [x] OneDrive storage-quota meter in the Library header (2026-10-06, user request "add
      tracking of available space on onedrive we're uploading to") — CONFIRMED showing
      correctly by the user. OneDriveClient.getDriveInfo (GET /me/drive → quota + owner facets,
      no extra OAuth scope); LibraryViewModel publishes quota/account/isSignedIn + refreshQuota
      (on Library open, ⟳ refresh, and after any upload/cloud-delete — NOT on the 4s reconcile
      timer); OneDriveStatusMenu/OneDriveQuotaView draw a used-fraction bar (amber/red on
      Graph's quota `state`) + "X free of Y". Only fetches when already signed in so opening the
      Library never pops a sign-in sheet. Branch resumable-onedrive-uploads (same branch as the
      resumable work; NOT merged to main yet).
- [ ] OneDrive account menu: click the meter → see signed-in account, Switch Account / Sign Out,
      or Sign In when signed out (2026-10-06, user request "see what [account] am I signed into
      and ability to switch it"). Account name/email from the drive `owner` facet. Signed-in
      display confirmed working; STILL TO CONFIRM: the Switch Account round-trip actually lands
      on a different account (Microsoft's sign-in page may silently reuse the old one — user
      must pick "Use another account" there), and Sign Out → Sign In from the Library header.
- [ ] OneDrive uploads now resumable across quit/crash/computer-restart (2026-10-05, user
      report "can't we make it so that progress is always saved… and recovered even after I
      restart a computer?"). Branch `resumable-onedrive-uploads` (NOT merged to main yet).
      Previously ANY interruption threw away progress and restarted from byte 0. Now the Graph
      upload-session URL (new RecordingMetadata.cloudUploadUrl) + per-chunk cloudBytesSent are
      persisted to library.json; OneDriveClient.uploadFile takes resumeUploadUrl/onSession and
      resumes from the server's nextExpectedRanges, recreates a session on the fly if it died
      mid-upload (404/410) instead of failing, retry budget 5->10. On launch,
      LibraryViewModel.resumeInterruptedUploads auto-restarts any .uploading/.creatingLink
      entry whose local file still exists (replacing the old demote-to-failed recovery).
      Builds clean; NOT verified end-to-end (see updates/2026-10-05 … Phase 3). CONFIRM:
      start a large upload, quit/restart partway, reopen Library → it resumes (bar not back to
      0) and finishes; share link unchanged after completion.
    - Caveat: if the server session has expired (multi-day), resume GET 404s and it restarts
      from byte 0 against the same item id (link preserved) — graceful fallback, not a failure.
- [ ] OneDrive nagging repeated sign-in on every cloud-button click (fix 2026-09-27, user
      report "constantly wants me to sign up to onedrive… why doesn't it just save it like
      before"): recordings always save locally regardless of OneDrive — that was never the
      problem. Root cause: OneDriveAuth.validAccessToken() called signOut() (deleting the
      Keychain refresh token) on ANY non-200 refresh response, so a single transient blip
      (5xx / 429 / flaky-connection empty body) permanently wiped a working sign-in and the
      next click had to redo the full device-code flow. Fixed: only signOut() on an explicit
      invalid_grant / interaction_required (token genuinely dead); every other failure throws
      a new .refreshFailed transient error that KEEPS the token so the next retry silently
      reuses it. MSA refresh tokens live ~90 days and auto-rotate on use, so one sign-in now
      lasts a long time. Built + installed to /Applications/RecBar.app. Note: because the old
      code already deleted the stored token, ONE more sign-in is needed next upload; after
      that it should stick. Confirm: sign in once, then several later cloud-button clicks
      (esp. after a network hiccup) no longer re-prompt.
- [ ] OneDrive uploads still failing on large files (fix 2026-09-23, follow-up to a4a9947):
      the timeout bump wasn't enough — real library.json failures were all mid-upload
      NSURLError transients (network-connection-lost, cannot-parse-response, timed-out) that
      each killed the whole upload with no retry, and the manual retry restarted from byte 0,
      so multi-hundred-MB / multi-GB files rarely finished across a flaky/slow upstream.
      OneDriveClient.uploadFile now retries each chunk up to maxChunkRetries (5) CONSECUTIVE
      failures with exponential backoff (capped 30s), resuming from the server's own
      nextExpectedRanges offset each time (Graph upload sessions are resumable). 4xx-non-429
      still fails fast; cancel still propagates. Confirm the previously-failed large files
      (Call Review - Miroslav, DealMakers Roleplay, Sales Call - Michal 2) now upload to
      completion — click the red exclamation-icloud icon to retry each.
    - Note (unrelated cosmetic): many uploaded entries have sizeBytes far smaller than
      cloudBytesSent in library.json, so the in-progress % bar denominator is wrong for
      those. Separate from the upload failures; not touched here.
